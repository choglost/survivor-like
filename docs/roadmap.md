
## 商业化开发路线图

如果目标是把当前原型做成一个完整的商业游戏，下一步不应该立刻堆内容，而是先把“可反复扩展、可测试、可调平衡”的生产管线建起来。

推荐按五个阶段推进：

```text
1. 原型稳固
2. 垂直切片
3. 内容生产
4. 质量与发布
5. 上线运营
```

每个阶段都应该有明确的完成标准。不要只按“写了多少功能”判断进度，要按“玩家是否能稳定体验一局完整游戏”判断。

### 第一阶段：原型稳固

目标：

```text
把当前原型整理成一个稳定、可扩展、可反复测试的核心循环。
```

重点工作：

```text
1. 完成元升级闭环
2. 完成局内升级闭环
3. 完成胜利/失败/重开流程
4. 修复明显脚本错误和命名问题
5. 整理配置数据，减少硬编码
```

建议优先完成：

- 永久升级至少 3 个，并且都能真实影响局内数值。
- 局内升级至少覆盖伤害、冷却、移速、范围、新技能。
- 经验、金币、掉落、升级、存档流程无明显断点。
- 一局游戏可以从主菜单开始，进入战斗，死亡或胜利后返回或重开。

推荐新增系统：

```text
RunStateManager
  管理一局游戏的开始、暂停、胜利、失败、结束。

GameBalance 资源
  集中管理经验曲线、刷怪曲线、掉落率、基础数值。

Debug/Cheat 工具
  快速加金币、加经验、触发升级、跳到某个时间点。
```

完成标准：

```text
玩家可以稳定完成一局 5-10 分钟的游戏。
核心循环没有阻断性 bug。
开发者可以快速调试升级、掉落和难度。
```

### 第二阶段：垂直切片

目标：

```text
做出一段可以展示给玩家或测试者的完整体验，而不是只展示系统。
```

垂直切片建议时长：

```text
10-15 分钟
```

垂直切片应该包含：

```text
1. 1 个完整地图主题
2. 3-5 种敌人
3. 1 个精英怪或小 Boss
4. 4-6 个主动/被动技能
5. 15-25 个局内升级
6. 5-8 个永久升级
7. 完整主菜单、设置、商店、结算界面
8. 基础音效、音乐、受击反馈、拾取反馈
```

这一阶段最重要的是“手感”。

需要重点打磨：

- 玩家移动是否顺滑。
- 攻击反馈是否清楚。
- 敌人是否有压迫感但不混乱。
- 经验和金币拾取是否爽快。
- 升级选择是否有明显期待感。
- 一局结束后是否有“再来一局”的动力。

完成标准：

```text
把游戏交给陌生玩家，不解释规则，玩家也能完成一局并理解成长目标。
```

### 第三阶段：内容生产

目标：

```text
在已验证的核心循环上批量扩展内容。
```

建议内容规模，可以根据你的商业目标缩放：

```text
地图：2-4 张
角色：2-4 个
敌人：10-20 种
Boss：3-6 个
技能：10-20 个
局内升级：50-100 个
永久升级：20-40 个
成就/挑战：20-50 个
```

为了支撑内容生产，需要把更多东西资源化。

建议资源化对象：

```text
EnemyData
  敌人血量、速度、伤害、掉落、权重、出现时间。

SpawnWaveData
  某个时间段的刷怪组合、权重、数量、特殊事件。

AbilityData
  技能图标、名称、描述、控制器、基础数值。

UpgradeData
  局内升级的 id、等级上限、描述、权重、前置条件。

MetaUpgradeData
  永久升级的等级、价格曲线、效果描述。
```

这时可以考虑引入统一效果系统。

例如：

```text
Effect
  id: "player_speed"
  target: "player"
  stat: "move_speed"
  operation: "multiply"
  value: 1.2
```

但不要过早做复杂编辑器工具。先把数据结构稳定下来，再决定是否做自定义编辑器面板。

完成标准：

```text
添加一个新敌人、新技能、新升级时，不需要改很多无关脚本。
大部分内容可以通过 .tres 资源配置完成。
```

### 第四阶段：质量与发布

目标：

```text
把游戏从“能玩”提升到“可以买、能评价、能维护”。
```

必须完成的质量工作：

```text
1. 存档稳定性
2. 设置菜单完整性
3. 键鼠和手柄输入
4. 分辨率和窗口模式适配
5. 音量、屏幕震动、特效强度等可调选项
6. 性能优化
7. 崩溃和错误日志检查
8. 新手引导
9. 本地化文本管理
```

Godot 项目中特别要注意：

- 大量敌人和掉落物时的节点数量。
- 频繁创建和销毁攻击物、特效、浮动文字的性能。
- 碰撞层和碰撞矩阵是否稳定。
- 资源路径移动导致的引用断裂。
- Web 导出和桌面导出的差异。

建议增加：

```text
ObjectPool
  用于浮动文字、经验球、简单攻击物、特效。

SettingsManager
  管理音量、窗口、语言、屏幕震动等设置。

Localization
  把 UI 文案、升级描述、技能描述从脚本/场景中抽出来。

SaveVersion
  给存档加版本号，未来可以迁移旧存档。
```

完成标准：

```text
连续多局游玩无阻断 bug。
玩家设置可以保存。
发布包可以稳定运行。
存档升级不会轻易损坏旧玩家数据。
```

### 第五阶段：上线运营

目标：

```text
让游戏在发布后可以继续被修复、平衡和扩展。
```

上线前准备：

```text
1. Steam 页面或发布平台页面
2. 宣传截图、GIF、短视频
3. Demo 版本
4. 玩家反馈渠道
5. 更新日志模板
6. 崩溃/错误反馈方式
7. 平衡表和版本记录
```

发布后重点：

- 观察玩家平均存活时间。
- 观察常用技能和冷门技能。
- 观察永久升级购买顺序。
- 观察玩家在哪些时间点死亡最多。
- 观察性能问题集中在哪些场景。

商业游戏不是一次性写完，而是持续调平衡。

建议保留这些记录：

```text
docs/balance.md
  记录关键数值、经验曲线、敌人曲线、掉落率。

docs/changelog.md
  记录每个版本的功能、修复、平衡调整。

docs/playtest_notes.md
  记录测试反馈、问题、调整结论。
```

## 当前项目的下一步执行计划

基于当前项目状态，建议从下面这个顺序开始做。

### 第 1 周：修稳核心循环

任务：

```text
1. 补完整元升级商店 UI
2. 增加 2-3 个永久升级
3. 增加调试快捷键或调试菜单
4. 把经验曲线、刷怪曲线、掉落率整理成资源或集中配置
5. 清理中文乱码注释和旧 TODO
```

推荐新增永久升级：

```text
experience_gain
  降低升级所需经验。

starting_gold
  每局开始时获得少量金币或提高金币掉落。

player_health
  提高玩家最大生命值。

move_speed
  提高玩家基础移速。
```

验收标准：

```text
商店可打开、可购买、可保存、下一局生效。
一局游戏可以完整开始和结束。
调试时能快速触发升级和获得金币。
```

### 第 2 周：扩展战斗内容

任务：

```text
1. 新增 1 个敌人
2. 新增 1 个精英敌人或小 Boss
3. 新增 2 个技能
4. 为每个技能补 2-3 个升级分支
5. 改善受击、击杀、拾取、升级反馈
```

验收标准：

```text
10 分钟内战斗节奏有变化。
玩家至少能形成 2-3 种不同构筑。
敌人组合不只是数值增加，而有行为差异。
```

### 第 3 周：做垂直切片

任务：

```text
1. 设计 10-15 分钟完整关卡节奏
2. 加入阶段性刷怪变化
3. 加入结尾 Boss 或生存胜利目标
4. 完善结算界面
5. 做一次完整 UI 统一
```

验收标准：

```text
陌生玩家能从主菜单进入、完成一局、理解永久成长，并愿意再开一局。
```

### 第 4 周：准备外部试玩

任务：

```text
1. 修复试玩反馈中的阻断 bug
2. 增加基础新手提示
3. 完成设置保存
4. 整理导出配置
5. 准备试玩包
```

验收标准：

```text
可以发给 5-10 个测试玩家试玩，并收集有效反馈。
```

## 商业化前的架构升级清单

下面这些升级建议按需要逐步做，不要一次性全部开工。

高优先级：

```text
1. SaveVersion：存档版本号和迁移
2. SettingsManager：设置保存
3. BalanceData：核心数值集中配置
4. DebugTools：快速测试升级、金币、时间、敌人
5. Localization：文案从场景和脚本中抽离
```

中优先级：

```text
1. EnemyData 和 SpawnWaveData
2. AbilityData 和 UpgradeData
3. ObjectPool
4. 统一伤害来源和伤害类型
5. 战斗日志或调试面板
```

低优先级：

```text
1. 自定义编辑器工具
2. 完整 ECS 化
3. 大规模目录重构
4. 复杂脚本热更新
```

当前项目最该避免的是：

```text
1. 在核心循环没稳之前疯狂加内容
2. 在技能数量很少时过度抽象
3. 让 UI 直接改核心数据
4. 把平衡数值散落在很多脚本里
5. 没有试玩就长期闭门调数值
```

## 商业化判断标准

当项目达到下面状态时，才算真正接近商业化版本：

```text
1. 玩家能无说明完成一局
2. 每局都有清晰成长和构筑选择
3. 局外永久成长能驱动下一局
4. 战斗反馈足够清楚
5. 内容量支撑至少数小时体验
6. 存档和设置稳定
7. 性能在目标平台稳定
8. 有可发布的 Demo 或试玩包
9. 有明确的差异化卖点
```

对这个项目来说，最可能的差异化方向可以从下面选一个：

```text
1. 更强的构筑组合和技能联动
2. 更有节奏的阶段刷怪和 Boss 战
3. 更明确的局外成长路线
4. 更鲜明的美术主题和角色设定
5. 更轻量、快节奏、适合短局的体验
```

建议先选一个主方向。商业游戏不一定要什么都有，但必须有一个玩家能记住的亮点。
